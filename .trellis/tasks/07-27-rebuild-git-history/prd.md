# 重建 Git 历史并保留上游贡献

## Goal

在保持 `tophtab/nga-just-works` 为可被 GitHub 默认仓库搜索发现的独立项目的同时，重建默认分支的祖先关系，使原项目贡献者的真实提交历史与本项目后续贡献形成一条可审计的历史链。

## Background

- 当前 GitHub 仓库 `tophtab/nga-just-works` 是独立仓库，不属于 fork network。
- 来源仓库是 `Justwen/NGA-CLIENT-VER-OPEN-SOURCE`；该仓库本身继承自 `ymback/NGA-CLIENT-VER-OPEN-SOURCE`。
- 已记录的导入基准是上游提交 `5d807617f8058950f7ea81dda405e38fb0cc37ec`。
- 上游基准历史包含 1489 个提交和数十位作者；这些提交当前不是本项目 `main` 的祖先。
- 当前 `main` 包含 53 个本项目提交，根提交为 `be26b6e07e5f6ac8fcbe505af5280ad95cc9e284`，迁移前端点为 `0e4c06600830e8d3e2adb373dd6a3f18e6592f40`，与上游不存在共同祖先。
- 仓库已有 5 个 GitHub Releases、本项目版本标签和调试标签；工作区存在用户未提交修改，且规划期间曾有新修改提交并推送，实际迁移必须以执行前的动态快照为准。
- `README.md`、`SOURCE_LEDGER.md` 和 `LICENSE` 已记录来源、基准、非官方性质和 GPLv2 许可。

## Requirements

- 重建后的默认分支必须以 `5d807617f8058950f7ea81dda405e38fb0cc37ec` 及其完整祖先历史为基础。
- 上游原始提交必须保持原 SHA、作者、时间、提交信息和父子关系，不得重写或伪造贡献归属。
- 当前 53 个本项目提交必须按现有顺序保留为 53 个逻辑提交，并保留各自的作者、提交者、时间、提交信息和文件树。
- 第 2 至第 53 个本项目提交的逐提交改动边界必须保持不变；第 1 个导入提交必须改为表达“上游基准到导入结果”的真实差异，不再把未修改的上游源码归入本项目贡献。
- 必须明确记录：由于父提交改变，本项目 53 个提交会生成新 SHA；这不属于提交丢失。
- 迁移前后的已跟踪最终文件树必须完全一致；历史重建不得改变当前产品代码、构建配置或文档内容。
- 执行开始时存在的全部未提交修改必须在迁移全过程中保持可恢复，并在完成后原样恢复；发布窗口内检测到并发修改时必须在远端改写前停止。
- 本项目版本标签和 GitHub Releases 必须映射到重建后语义相同的本项目提交；上游已有标签不得被误改或覆盖。
- GitHub 仓库必须继续保持独立仓库状态，不执行临时 Fork 后脱离 fork network 的迁移路线。
- 迁移后必须继续保留清晰的上游链接、基准提交、许可证和非官方衍生项目声明。
- 任何公开分支改写前必须建立本地和远端可验证备份，并提供明确回滚点。
- 发布期间必须阻止 `main` 和版本标签的强制更新触发 Android 构建或改写 Releases，并在结束或失败后恢复原 Actions 权限。

## Key Decisions

- 接受本项目现有 53 个提交全部生成新 SHA，以获得线性的真实上游祖先关系。
- 保持当前 GitHub 仓库独立，不执行临时 Fork 或 leave fork network。
- 保留所有现有公开标签名称和 Release 链接；含旧 SHA 的调试标签名称作为历史发布标识保留，同时将目标映射到相同文件树的新提交。
- 迁移以对象级重建完成，不使用会重新应用补丁并产生内容漂移的普通 rebase。

## Out of Scope

- 不清理、压缩或重新组织上游提交历史。
- 不借本次迁移重构当前 53 个本项目提交或修改产品代码。
- 不把当前仓库转换为 GitHub Fork，也不尝试加入或离开 fork network。
- 不保证所有历史邮箱都能匹配到 GitHub 账号头像或个人贡献日历；只保证原始提交身份和历史可达性。
