# 主题页两页预读取策略

## Goal

在用户阅读在线主题时提前准备当前页之后的最多两页以减少翻页等待，但始终不预读取当前已知的最后一页，使末页在真正打开时获取最新回复。

## Background

正常主题详情使用 `ArticleTabFragment`、`ArticlePagerAdapter` 和每页一个 `ArticleListFragment`。成功响应中的 `ThreadData.__ROWS` 由父 Fragment 按 `ceil(__ROWS / 20)` 转换为总页数。Pager 使用 `BEHAVIOR_RESUME_ONLY_CURRENT_FRAGMENT`，当前实现只有真正恢复的页会请求数据，因此尚无实际预读取。

离线文章缓存由 `ArticleCacheActivity` 处理，帖子内搜索由 `ArticleSearchFragment` 处理，两者不进入本任务。

## Requirements

- R1. 仅在线正常主题 Pager 启用预读取；离线缓存阅读和帖子内搜索路径保持不变。
- R2. 当前页成功加载并得到总页数后，将 `currentPage + 1` 与 `currentPage + 2` 作为唯一候选页。
- R3. 只调度满足 `candidatePage < totalPages` 的候选页；等于最后一页或超出总页数的页绝不预读取。
- R4. 示例必须成立：当前第 3 页、共 6 页时预读取 4、5；共 5 页时只预读取 4；共 4 页时不预读取。
- R5. 预读取在后台静默执行，不阻塞当前页、不显示刷新态/Toast/错误页、不自动打开 WebView，也不因失败触发面向用户的账号轮换流程。
- R6. 成功预读取的数据仅在当前主题 Activity 生命周期内复用；用户打开该非末页时不发起重复并发请求。
- R7. 若用户在预读取进行中进入该页，继续复用同一请求；请求成功即展示，若请求失败则自动转入现有正常前台加载与错误处理路径。
- R8. 预读取失败或取消不影响当前页。目标 Fragment/Activity 销毁时沿用现有 RxLifecycle 取消，不把数据泄漏到其他主题。
- R9. 当前页变化或最新 `__ROWS` 改变总页数时重新计算候选集合；仍只保留当前页之后两页且排除最后一页。
- R10. 用户下拉刷新当前页时继续执行现有显式前台刷新，不被已预读取数据拦截。
- R11. `THREAD.PAGE` 的 URL、字段、Cookie 传递、解析器和正常前台失败处理保持不变。

## Acceptance Criteria

- [ ] AC1（R2-R4）：纯规划逻辑对 `(3,6)` 返回 `[4,5]`、对 `(3,5)` 返回 `[4]`、对 `(3,4)` 返回空，并覆盖首页、倒数第二页、末页和非法边界。
- [ ] AC2（R3）：任何调度记录中都不存在 `page == totalPages` 或 `page > totalPages`。
- [ ] AC3（R5）：后台失败不显示 Toast、刷新态、WebView 或其他前台错误 UI，也不影响当前页阅读。
- [ ] AC4（R6-R7）：打开已成功预读取的非末页直接复用结果；预读取进行中切入不会产生重复请求；失败后正常前台加载可恢复。
- [ ] AC5（R8-R9）：快速切页、总页数更新和页面销毁不会跨主题复用数据或留下失控请求。
- [ ] AC6（R10-R11）：下拉刷新、正常请求重试、解析和手动离线缓存功能无回归。
- [ ] AC7（R1）：`ArticleCacheActivity` 与 `ArticleSearchFragment` 不启用本预读取策略。
- [ ] AC8：自动化测试覆盖规划器、调度触发、末页排除、静默失败、请求去重和前台回退合同。

## Out of Scope

- 对最后一页进行预读取后再增量刷新或合并新评论。
- 修改每页 20 条的现有页数计算、服务端分页或回复排序。
- 将预读取扩展到当前页之后超过两页、主题列表或离线缓存文件。
- 新增持久化磁盘缓存、跨 Activity 共享缓存或预读取设置开关。
